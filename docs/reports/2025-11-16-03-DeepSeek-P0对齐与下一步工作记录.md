### 3.2 DeepSeek 指标体系统一与去重

#### 3.2.1 修改目标与原因

- 原状问题：
  - `src/local/deepseek-reasoning-server.py` 中存在以下 Prometheus 指标命名与语义冲突：
    - 全局中间件使用：`deepseek_request_total`、`deepseek_request_duration_seconds`。
    - 业务侧额外定义：`deepseek_requests_total`（复数）、`deepseek_request_latency_seconds`、`deepseek_inprogress` 等。
  - 这种重复与命名不一致会导致：
    - Grafana 查询与告警规则难以统一；
    - `requests_total` vs `request_total` 等写法上容易产生误用；
    - 时延直方图与时延摘要名称不统一。

- 目标：
  - 以“补齐版 v1.1”与实际 Grafana fixed.json 中使用的 PromQL 为基准，对 DeepSeek 服务的指标做 **统一命名** 与 **去重**：
    - 请求计数：`deepseek_request_total{method, endpoint, status}`
    - 错误计数：`deepseek_errors_total{endpoint}`
    - 时延直方图：`deepseek_request_latency_seconds_bucket`（由 Histogram `deepseek_request_latency_seconds` 自动派生）
    - 并发：`deepseek_inprogress`（Gauge）

#### 3.2.2 实际代码改动

> 文件：`d:/AI-Projects/projects_share_structure/src/local/deepseek-reasoning-server.py`

- **统一全局指标定义**：
  - 原始片段（问题点）：
    - 中间件层：
      - `REQUEST_COUNT = Counter('deepseek_request_total', ...)`
      - `REQUEST_LATENCY = Histogram('deepseek_request_duration_seconds', ...)`
      - `ACTIVE_REQUESTS = Gauge('deepseek_active_requests', ...)`
    - 实例级：
      - `self.requests_total = Counter("deepseek_requests_total", ...)`
      - `self.request_latency = Histogram("deepseek_request_latency_seconds", ...)`
      - `self.inprogress = Gauge("deepseek_inprogress", ...)`

  - 修改后：
    - 全局仅保留一组 DeepSeek 指标：
      - `REQUEST_COUNT = Counter('deepseek_request_total', 'Total requests', ['method', 'endpoint', 'status'])`
      - `REQUEST_LATENCY = Histogram('deepseek_request_latency_seconds', 'Request latency (s)', ['endpoint'])`
      - `ACTIVE_REQUESTS = Gauge('deepseek_inprogress', 'In-progress requests')`
      - `self.errors_total = Counter('deepseek_errors_total', 'Total errors', ['endpoint'])`
    - 移除实例级 `self.requests_total` / `self.request_latency` / `self.inprogress`，避免重复计算。

- **中间件路径统一记录时延与状态码**：
  - 正常路径：
    - `REQUEST_COUNT.labels(method, endpoint, status=response.status_code).inc()`
    - `REQUEST_LATENCY.labels(endpoint=request.url.path).observe(process_time)`
  - 异常路径：
    - 区分 `HTTPException` 与其他异常：
      - 若为 `HTTPException`，使用 `e.status_code`；否则记为 500。
    - 同样记录时延：`REQUEST_LATENCY.labels(endpoint=request.url.path).observe(process_time)`。

- **业务端点复用统一 Histogram**：
  - `/tools/{tool_name}/invoke` 与 `/reasoning`：
    - 使用 `with REQUEST_LATENCY.labels(endpoint="tool_invoke").time(): ...` 和 `with REQUEST_LATENCY.labels(endpoint="reasoning").time(): ...` 记录端点级 P95 基线所需直方图。
    - 去除额外的 `self.requests_total` 递增，避免双计数。


### 3.3 并发限流策略微调

> 文件：`d:/AI-Projects/projects_share_structure/src/local/deepseek-reasoning-server.py`

- 原始行为：
  - 在 `/tools/{tool_name}/invoke` 和 `/reasoning` 中，获取并发控制信号量：
    - `await asyncio.wait_for(self._semaphore.acquire(), timeout=0.05)`
  - 0.05 秒是非常激进的等待时间，在轻微抖动或垃圾回收等场景下，容易将原本可以排队完成的请求误判为 429：
    - 这在之前的并发压测中表现为高比例 429。

- 修改后行为：
  - 将超时从 `0.05s` 提升到 `0.3s`：
    - `await asyncio.wait_for(self._semaphore.acquire(), timeout=0.3)`
  - 设计意图：
    - 保持“有上限的排队时间”，避免无界排队；
    - 同时为短暂抖动留出适度缓冲，减少误伤 429；
    - 仍保留 P0 阶段对 `429_ratio` 的告警与 Canary 判定能力。

> 说明：
> - ACTIVE_REQUESTS(`deepseek_inprogress`) 现由 HTTP 中间件统一管理，端点内部不再重复 inc/dec，以免产生“翻倍”的并发数。

   - 把 DeepSeek 推理服务（MCP Server）**注册为 Autogen 的工具/能力**，  
     让现有/未来的 Agent 能像用其它工具一样调用它。  
   - 入口统一走 Autogen 的对话/Agent 流水线，而不是另写一套调度器。

2. **任务/向量/日志的“事实来源”是谁？**  
   - 任务元数据、向量索引、执行记录等，**落在 UnifiedStorage 这一个“真相库”里**，  
     而不是混合算力这边再造一套 TaskDB 或 VectorDB。  
   - DeepSeek/MCP 这边只负责“执行 + 指标 + 对象存储旁路”，不抢 UnifiedStorage 的角色。

3. **MCP 服务的注册/发现由谁负责？**  
   - 让 MCP 服务（包括 DeepSeek 和未来的 image/video 之类）  
     **在 Registry 里注册/发现**，复用现有能力，而不是在混合算力侧自建一套“服务发现表”。

PoC 级别只要求：  
- 至少有 **一个 DeepSeek 工具** 能从 Autogen 里被正常调用；  
- 对应的任务/向量/元数据写入 UnifiedStorage；  
- MCP 实例在 Registry 中出现并能被查到。  

即：证明“这条路打得通”，不要求你现在就把所有业务都迁过去。

## 三、和当前你已经做的底座工作，怎么合在一起？

你现在的混合算力技术底座（补齐版 + DeepSeek + MinIO + 监控）主要解决的是：

- **网络 & 执行 & 数据旁路 & 观测/安全**  
  - VPN / ACL / MCP / MinIO / Prometheus / （未来的）Grafana & 告警 & OTel。  
- **P0 运行基线**  
  - DeepSeek 指标统一  
  - 并发与 SLO 基线（MAX_CONCURRENCY=1, P95≈0.39s）  
  - 数据走对象存储旁路，不在 MCP 内搬大文件。

把 Autogen + UnifiedStorage + Registry 接进来，并不是要把现有这一套推翻重做，而是：

- **上面挂一个“调度大脑”和“统一事实库”**：  
  - 调度层：谁来决定把某个推理/ETL/向量任务发到哪台 MCP 服务器。  
  - 存储 & 注册层：任务状态、向量索引、MCP 服务注册这类“全局视角”的信息。

- **下面保留你已经打磨好的执行底座**：  
  - 具体跑活的是 DeepSeek/MCP + MinIO + 监控体系。  
  - Autogen 调度只是“派活 + 记录 + 观测”，不重写执行逻辑。

  - 运行一次轻量 `bench-reasoning.py`，确认 `r429≈0` 且 `P95≤0.45s`；  
  - 可选：运行 `e2e-deepseek-job.py`，确保 MinIO 输入→推理→输出闭环正常。

### 2. 服务器侧代码获取（在线 / 离线两种方式）

- **若服务器可访问 GitHub**：  
  - 在服务器上执行：  
    - `git clone https://github.com/xm-fieldservice/feature-server-poc-vpn.git <目标目录>`  
    - `cd <目标目录>`  
    - `git switch feature/server-poc-vpn`  

- **若服务器暂时无法访问 GitHub（离线方式）**：  
  - 在本地将当前仓库目录打包为压缩包（排除 MinIO 数据等大体量目录按需处理）。  
  - 通过 U 盘 / 内网传输将压缩包拷贝至服务器并解压。  
  - 可选：在服务器目录内执行 `git init`，未来网络恢复后再补充 `remote add origin` 与 `git fetch`，保持历史可追溯。

### 3. VPN 与网络配置（只列原则）

- **专用网段**：  
  - 为“服务器 ↔ 本地机”建立专用 VPN 网段（例如 10.x.y.0/24），避免与其他业务混用。  
- **最小暴露面**：  
  - 在 VPN 配置与本地防火墙中，只允许：  
    - 服务器 VPN IP → 本地 VPN IP；  
    - 访问端口限定为：DeepSeek HTTP 端口、MinIO 端口（以及可选的 Prometheus 抓取端口）。  
  - 不通过 VPN 暴露本地其他服务端口。  
- **DNS / 访问方式**：  
  - 可直接使用本地 VPN IP + 端口，例如：  
    - `http://<本地-VPN-IP>:<deepseek-port>/health`  
    - `http://<本地-VPN-IP>:<deepseek-port>/metrics`  
    - `http://<本地-VPN-IP>:9000`（MinIO 控制台 / API）。

### 4. 服务器侧联调验证步骤

- **基础连通性**：  
  - 在服务器上执行：  
    - `curl http://<本地-VPN-IP>:<deepseek-port>/health`  
    - `curl http://<本地-VPN-IP>:<deepseek-port>/metrics`  
  - 预期：/health 返回 200，/metrics 输出包含 `deepseek_request_total` 等指标。  

- **SLO 视角验证**：  
  - 在服务器上运行 `bench-reasoning.py`，将 URL 指向本地 DeepSeek 的 VPN 地址：  
    - 观察 P95、429 比例、成功率与本地压测结果的一致性或可接受偏差。  

- **E2E 路径验证（如需要）**：  
  - 在服务器侧模拟“控制平面”：  
    - 通过 VPN 访问本地 MinIO，写入 `inputs/<job_id>/input.json`；  
    - 触发本地 `scheduler-poller.py` 轮询与 /reasoning 调用；  
    - 确认 `outputs/<job_id>/result.json` 被写回，并包含 Job 字段（state/attempts/timestamps 等）。
